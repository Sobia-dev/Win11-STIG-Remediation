# WN11-AU-000505 – Security Event Log Size

## Summary

- **STIG ID:** WN11-AU-000505 (Vuln ID V-253338)
- **Severity:** CAT II (Medium)
- **Requirement:** The Security event log max size must be **5120000 KB (~4.9 GB) or greater**
- **Registry:** `HKLM\SOFTWARE\Policies\Microsoft\Windows\EventLog\Security` → `MaxSize` (REG_DWORD)
- **Script:** [WN11-AU-000505.ps1](WN11-AU-000505.ps1)
- **Status:** ✅ Remediated and verified (Tenable audit: **Passed**)

## Why It Matters

- The Security log records logons, failed logons, privilege use and account changes, so it's the core evidence source for incident response.
- The Windows default is small (20 MB). On a busy system, old events get overwritten within hours.
- Attackers can flood the log on purpose to push their earlier activity out.
- A larger log keeps more history available for threat hunting, investigations and audits.
- Maps to CCI-001849 (allocate enough audit record storage capacity).

## Initial Remediation – Failed

- Researched the rule. Public sources (Tenable's audit page, Google AI Overview) listed **1024000 KB**.
- Wrote a PowerShell script setting `MaxSize = 1024000` and ran it on the lab VM.
- Rescanned with Tenable → **Failed**.
- Ran `gpresult` → no GPOs applied, so no domain/Intune policy was overwriting the setting.
- Opened the audit details in Tenable:
  - **Output (actual):** `1024000`
  - **Policy Value (required):** `[5120000..4294967295]`
- **Root cause:** the 1024000 KB value came from **DISA Windows 11 STIG v1r4**, which Tenable marks as **deprecated**. My scan used a newer audit version that requires **5120000 KB**.

## Fix – Passed

- Updated the script: `$RequiredSize = 5120000`
- Re-ran the script as Administrator → registry now shows `0x4e2000` (5120000).
- Ran `gpupdate /force` to apply.
- Rescanned with Tenable → **Passed** ✅

## Verification Commands

```powershell
# Registry value (expect 5120000 / 0x4e2000)
reg query "HKLM\SOFTWARE\Policies\Microsoft\Windows\EventLog\Security" /v MaxSize

# Live log size Windows is using (expect 5242880000 bytes)
Get-WinEvent -ListLog Security | Select-Object LogName, MaximumSizeInBytes
```

## Lessons Learned

- **Trust the scan's Policy Value, not public docs.** STIG values change between releases, and search results can show deprecated versions.
- **Read the audit details** (Actual vs. Policy Value) before guessing. It pinpointed the problem right away.
- **Rule out policy overrides** with `gpresult` when a fix doesn't stick.
- **Always rescan** to prove the fix. A script saying "PASS" isn't the same as the audit passing.
- Account for disk space. A ~4.9 GB log cap needs room on the system drive.
